# 미팅노트 텍스트 → DB 레코드 변환 규칙

사용자가 미팅노트 txt 파일(카톡 GIS_미팅노트방 내보내기 등)이나 메모 텍스트를 주면 이 규칙으로 레코드를 만들어
`scripts/upsert.mjs`로 DB에 넣는다. 순서는 `CLAUDE.md`.

> **원칙 — 원문은 그대로, 앞에는 요약정리.** 원문 메시지는 `raw`에 **한 글자도 고치지 않고** 넣는다(앱의 '원문' 탭).
> `body`는 앱이 먼저 보여주는 **요약정리**로, 기존 미팅처럼 섹션으로 나눠 정리한다(2026-11-05 사용자 요청).
> 요약정리는 원문에 있는 사실만 — 지어내기·해석 추가 금지, 숫자·고유명사·영문 용어는 원문 그대로. `upsert.mjs`가 숫자 근거를 raw와 대조한다.

이 문서는 공개 저장소에 있으므로 일반 규칙만 둔다. **기관 약칭 해석표·KB 게시자 표기·알려진 이름 충돌**처럼
고객·인물이 드러나는 표는 암호화된 DB 안 `ref.convertSpec`에 있다. 복호화한 뒤 반드시 함께 읽는다.
기관명은 DB `orgs[].name`·`orgs[].aliases`로 맞춘다.

## 미팅 레코드 (meetings) — 모든 필드 필수
| 필드 | 규칙 |
|---|---|
| `id` | `YYYYMMDD-<ascii-slug>` 고유. slug는 기관 id(orgs의 id, 예: 공제회 약칭 영문)에 부서 꼬리 붙이기(`-re`, `-infra`, `-corp`). 같은 날 같은 기관 2건이면 `-2` |
| `date` | 텍스트에 적힌 미팅일. 없으면 게시일. 불확실하면 flags `날짜 확인: …` |
| `org` | 표준 기관명(orgs의 name). 처음 보는 기관이면 patch의 `orgs`에 새 기관도 추가 |
| `orgType` | 연기금·공제회·보험·운용사·은행·증권·캐피탈·저축은행·기타·GP·내부 |
| `dept` | 상대 부서·팀(알면) |
| `category` | LP·GP·시장정보·내부. KB증권 운용부서(발행어음·헤지 등)와의 미팅은 LP |
| `attendees` | 상대측 참석자, 줄마다 `이름 직급 - 소개`. 직급 약어는 풀어도 되지만(분류용), 소개는 원문 표현 그대로 |
| `kbAttendees` | 게시자 또는 명시된 KB 참석자(예: `홍길동 차장`) |
| `assets` | 아래 전략 키만 |
| `body` | 요약정리(아래 "body — 요약정리") |
| `raw` | 이 미팅에 해당하는 원문 메시지를 한 글자도 고치지 않고 그대로(카톡이면 날짜·게시자 줄 포함). 앱의 "원문" 보기 |
| `rawShared` | 한 게시물을 여러 미팅으로 나눈 경우 true — raw 에 다른 미팅 내용도 함께 있다는 표시(원문 탭에 안내) |
| `legacyBody` | 2026-10-30 이전 변환본이면 true(참고용 표시). 요약정리 형식은 지금 규칙과 같다 |
| `nextAction` | 원문에 명시된 다음 액션·후속 일정만(원문 표현을 살려 짧게), 없으면 `""` |
| `tags` | 짧은 키워드 8개 이하(GP명, 이슈, `인사이동`, `재간접`, `RFP` 등) |
| `flags` | `원문 잘림`, `내부용`, `날짜 확인: …`, `이름 확인: …`, `추정: …` |
| `source` | `카톡 GIS_미팅노트방 · YYYY-MM-DD 게시 · <게시자>` 또는 `직접 입력 · YYYY-MM-DD` |
| `truncated`·`truncAt` | 원문이 잘려 끝나면 true와 잘린 지점 문장 |

## body — 요약정리
원문을 읽기 쉽게 섹션으로 나눈 요약. 앱에서 먼저 보이는 탭이다. 원문은 `raw`에 따로 그대로 있다.

**섹션**
- LP: `*조직/인사 및 운용 규모` → `*최근 투자현황/계획` (내용 없는 섹션은 뺀다)
- GP: `*운용사/펀드 현황` → `*논의 내용` / LP·GP 함께한 미팅은 `*운용사/펀드 현황` → `*(LP) 현황` → `*논의 내용`
- 시장정보·내부: `*내용`
- 섹션 아래 줄은 모두 `- `로 시작. `--> ` 줄은 원문에 명시된 Next Step·결론·시사점이 있을 때만(새 해석 추가 금지)

**쓰는 법**
- 개조식 음슴체(~함/~임/~음). 원문 순서를 크게 바꾸지 않고 같은 주제끼리 섹션에 모은다
- 숫자·통화·날짜·고유명사(기관·GP·펀드·사람 이름)·영문 실무 용어는 **원문 그대로**(USD 50m, 1,000억원, Re-up, Final Closing …)
- 원문에 없는 사실·숫자·평가·해석을 넣지 않는다. 애매한 건 원문 표현을 살린다
- 원문 글머리표(`-`·`•`·`*`)는 `- `로. body 의 `*`줄은 소제목이므로 원문의 `* ` 글머리표를 그대로 두지 않는다
- 동료 보충은 `- (홍길동 과장 보충) …`
- 원문이 잘려 끝나면 마지막 줄 뒤에 `- (원문 잘림 — 카톡 '전체보기'로 확인 필요)` + flags `원문 잘림` + truncated
- 원문 첫 줄(날짜·기관·참석자 머리)은 분류용 필드(date·org·dept·attendees)로 옮긴다

**나누기·빼기:** 여러 기관을 한 메시지로 묶은 시장정보는 기관별로 레코드를 나누되 각 body는 해당 부분만, raw는 메시지 전체(rawShared).
여러 메시지로 나눠 올린 한 미팅(`[… 1/4]`~`[… 4/4]` 등)은 레코드 하나로 합치고 raw에 모두 시간순으로.
초대·퇴장, 삭제된 메시지, 파일 공유만 있는 메시지(GP 미팅 자료는 `첨부: 파일명` 레코드로), 행정 대화는 뺀다.
`외부공유x`·`내부용`·`내부 참고용` 표시 → flags `내부용`.

**카톡 원문:** raw 는 `scripts/kakao.mjs`가 묶은 게시물 원문 그대로(각 메시지의 "2026년 4월 16일 오후 4:47, 이름 : " 머리 줄 포함).
미팅에 보충·대화가 합쳐졌으면 그 게시물들도 시간순으로 빈 줄 하나를 사이에 두고 이어 붙인다. 카톡 내보내기는 한 메시지를
500자에서 자르므로, 495자 이상인 메시지로 끝나면 원문 잘림으로 표시한다. 대화로 받은 메모도 같은 미팅이면 raw 뒤에 그대로 덧붙인다.

**검사:** `upsert.mjs`는 body를 준 미팅에 raw가 있으면 요약정리의 숫자가 모두 raw에 있는지 보고, 없으면 저장하지 않는다
(사용자가 직접 고쳐 달라고 한 때만 `--allow-edits`). 원문에 없는 영문 단어는 경고 — 표기를 확인한다.

## 인물 (people)
- 미팅에 나온 외부 인물(KB 직원 제외)을 patch `people`에 넣는다: `name`, `org`(표준명), `dept`, `title`, `note`(원문 근거 한 줄),
  `lastSeen`(미팅일), `source`(`미팅노트 YYYY-MM-DD`)
- 이미 있는 사람이면 upsert가 합친다(빈 연락처만 채움, note·source 덧붙임, 더 최근이면 직급 갱신)
- 인사 정보(이동·승진·휴직)는 note에. 기존 표기와 이름이 다르면 flags `이름 확인: …`

## 기관 시그널 (orgs.signals)
- 미팅에서 전략별 의향이 분명히 나오면 patch `orgs`에 `signals: {전략: {s, note, date}}`로 갱신
- s: `약정`(올해 약정 완료) · `진행`(실사·심의·선정 중) · `관심`(검토 의향) · `보류`(일시 중단) · `불가`(규정·방침상 어려움)
- note는 짧게(예: `유럽 DL 확대`), date는 미팅일. 추정이면 갱신하지 않는다
- 새 약칭이 나오면 그 기관 `aliases`에 추가
